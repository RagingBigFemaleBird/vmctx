=== 0a789fb79 2026-07-27
vmctx: a VM context as a first-class Linux process

Adds a kernel facility that lets an ordinary process run its own user code
as a hardware-virtualized guest, on its own page tables, while remaining an
ordinary process: schedulable, killable, forkable, debuggable, and visible
in /proc. The hardware backend lives out of tree (AMD SVM and Intel VMX);
this is the generic half that everything else attaches to.

  1301 insertions across 16 files, on vanilla 6.18.35.

WHAT THIS IS

A VM context is not a virtual machine. There is no guest kernel, no virtual
devices, no separate address space. The guest is the calling process's own
user code, executing at CPL3 on the process's own page tables, with
second-level translation (NPT/EPT) mapping guest-physical to host-physical
identically. What virtualization buys is a boundary: every fault and every
syscall the guest makes leaves the guest and can be answered somewhere
else — by this kernel, or by a monitor process, or by a different machine
entirely.

The point is that a process's execution can be separated from the resources
its execution needs. Code and memory can live on one machine while the
files, sockets and kernel state they act on live on another.

WHAT IT ADDS

  include/uapi/linux/vmctx.h   the ABI: vmctx_run(2), vmctx_ctl(2), the
                               event and reply structures, the flags
  include/linux/vmctx.h        struct vmctx_task, the backend interface,
                               the hooks the core calls
  kernel/vmctx.c               the core: context lifecycle, the run loop,
                               generic syscall dispatch, monitor redirection
  arch/x86/kernel/vmctx.c      the x86 syscall-dispatch shim
  kernel/entry/common.c        guest entry from the return-to-user path
  kernel/fork.c, exit.c        a context that forks; a context that ends
  fs/exec.c                    a context that execs
  fs/proc/array.c              a context visible in /proc

  vmctx_run(2)   turn the calling process into a VM context and run it
  vmctx_ctl(2)   a monitor process drives another task's context:
                 ATTACH, DETACH, WAIT, RESUME, GETREGS, SETREGS, PEEK, POKE

FIVE DESIGN DECISIONS, EACH ARRIVED AT THE HARD WAY

1. The guest runs from the return-to-user path. vmctx_guest_step() is
   called from exit_to_user_mode_loop(), so the guest runs exactly where
   the kernel would otherwise have returned to userspace. Everything the
   scheduler and the signal machinery already do at that point keeps
   working, unchanged, for free.

2. The task's pt_regs is the canonical guest register frame. Not a private
   copy synced occasionally — the frame itself. Signal delivery, syscall
   restart, rt_sigreturn, ptrace and /proc therefore operate on guest state
   without knowing that a guest exists. When arch_do_signal_or_restart()
   rewinds RIP by two on -ERESTARTSYS, it lands on the guest's SYSCALL
   instruction, because that is what the frame describes.

3. Syscalls dispatch through the host's own syscall table. There is no
   per-syscall code in vmctx and no allow-list: a guest syscall is
   marshalled into a pt_regs and run through x64_sys_call(). The deny list
   started long and is now empty. Breadth came from refusing to enumerate.

4. Faults are the host's own demand paging. The guest runs on the process's
   page tables, so a not-present guest page is an unpopulated page of this
   mm; fixup_user_fault() handles it and the instruction retries. Nothing
   needs to know what the guest was doing.

5. Fork, exec and threads are the kernel's, not ours. copy_thread() has
   already prepared the child's frame correctly — RAX zero, RSP inherited
   or the new thread's stack — so the backend copies the parent's context
   and takes the child's registers from its own pt_regs. Threads need no
   special case; that is why they work. clone() with CLONE_VM shares the
   address space, so the kernel keeps one context and there is no child to
   follow: treating that as a fork means waiting for a child that never
   appears.

MONITOR REDIRECTION, AND TWO BUGS IN THE HANDSHAKE

A monitor process can service a context's faults and syscalls instead of
the kernel. The context publishes an event, wakes the monitor, and sleeps
until it replies. Two failures in that handshake took a long time to see,
and both are worth recording because their symptoms pointed elsewhere.

A monitor may be slow without being dead. The reply wait used a deadline,
so a monitor that took its time was declared gone and the kernel answered
the event itself — which for a context whose memory lives on another
machine means fabricating an anonymous zero page. The guest then ran blank
memory and died somewhere unrelated with nothing in the log. Liveness is
polled now: the question is whether the monitor is alive, not how fast it
answers.

A signal must not make a syscall run twice. The wait gave up on a signal
and returned VMCTX_ACT_RETRY, which rewinds the instruction so the guest
executes it again — right for a fault, wrong for a syscall that has already
run elsewhere, with its effects. A program read its resolver child's
answer, took the SIGCHLD that child had just sent, re-executed the read,
got the one trailing byte after the answer, and concluded the lookup had
failed. Once the monitor has dequeued an event the wait is no longer
interruptible; the signal is delivered on the way back to userspace, which
is where a syscall's signals are delivered anyway. Separately, discarding
an abandoned event's late reply also cleared ev_pending — which by then
belonged to the event the context had already re-published — leaving the
context waiting for a reply nobody knew to send and the monitor waiting for
an event no longer on the queue.

WHAT IT IS NOT

Guest syscalls bypass seccomp, audit and ptrace syscall-stops: they are
dispatched through the syscall table, not through the entry path that
carries those. A context is as privileged as the process that created it
and is not a sandbox. [vvar] and [vdso] cannot be transplanted between
machines and are zero-filled when they are absent, which is logged loudly.

VERIFIED ON HARDWARE

Every claim was measured on real machines — AMD Ryzen 7 4800H (SVM) and
Intel Core i7-7700K (VMX) — never in emulation. A browser installed only on
one machine runs on the other and renders byte-identical output; in-guest
compute runs at 99.9% of native on the same silicon.

=== 6258d2b23 2026-07-27
vmctx: wake the context that is waiting uninterruptibly for its reply

  elinks -dump, both ends on one machine   2.5 s  ->  0.51 s

A context waiting for its monitor's answer sleeps uninterruptibly once the
monitor has dequeued the event — deliberately, because giving up there would
re-run a syscall that has already executed on the other machine. But the
monitor answered it with wake_up_interruptible(), which matches only
TASK_INTERRUPTIBLE sleepers and passed this one by. The reply was sitting
there; the context slept until the 2-second monitor poll expired, re-checked,
found it, and carried on. Correct output, two seconds later.

It needs a signal to arrive while the monitor holds the event, so it never
showed on a short program — and a guest that forks is guaranteed one, since
SIGCHLD arrives the moment its child exits. elinks forks even to render a
local file, so eight runs in ten paid it.

Found by timing what is neither fault nor forwarded syscall. That was 2.1 s
of a 2.5 s run, and the guest turned out to be in state D in vmctx_report
with close(7) outstanding — for exactly VMCTX_MONITOR_POLL.

Every wake of reply_wq gets the same treatment: attach, detach and resume can
all be answering a context in that wait.

Verified: 8/8 on AMD and both LAN directions byte-identical, elinks over HTTP.

=== 1a3d30044 2026-08-01
vmctx: an exception event says which exception it was

A reported fault carried an address and an error code but no vector, so the
only exception that could be reported at all was the page fault. Every other
one ended the context where it was raised, because there was no way to say
what it had been -- and vmctx_report() is static, so a backend could not
build the event itself either.

The vector now travels in the event's spare number field, unread on the way.
Which signal a vector becomes, or whether it becomes a signal at all, is the
owning system's rule and not this one's; a context whose owner is not Linux
would answer differently to the same report. So the kernel says 6, 13 or 14
and interprets none of them.

=== 8bb572c15 2026-08-01
vmctx: a mapping may name where in the backing object it comes from

Everywhere else a guest virtual address is its own offset, which is what
lets two contexts started with one object see the same page at the same
address -- a thread, on a machine with no CLONE_VM. It also makes aliasing
impossible: two addresses are two offsets and so two pages, permanently.

Shared memory is aliasing. A reply may now say where the bytes come from
instead of it being implied, and the ordinary case passes the address back
unchanged. Only the side holding the file can know that two mappings are one
page, so it is the side that says so.

=== 671635d74 2026-08-01
vmctx: a context may hold a shared object beside its own memory

backing_fd is a context's own memory: a thread is handed its parent's, a
process a copy, and that copy is what fork means. Shared memory is the one
thing a fork must not copy, and an offset cannot express it -- two offsets in
two different objects are two pages however they are numbered.

So a second descriptor, in padding the config already had, inherited as it is
rather than copied, and a map action that reads a range from it. A fault's
answer may carry a mapping as a syscall's always could, because a context
that inherited a shared range got it from the copy and its first touch is
when to say otherwise.

=== 4242de49b 2026-08-01
vmctx: a shared mapping with no object is refused, not made private

A NULL file means MAP_PRIVATE|MAP_ANONYMOUS in vm_mmap, which is right for a
context given no memory object at all and wrong for a range the owner called
shared: the guest gets private zeroed memory, every read of it comes back

=== b4bdd964e 2026-08-01
vmctx: a fault says what this side knows about the page

A page's permissions answer to two masters -- the program, whose protections
live in the VMA, and the coherence protocol, which write-protects the PTE and
leaves the VMA alone. Told only an address and an error code, a monitor
decides between them from its own records and guesses when they are silent.
The event's argument words are unused on a fault, so the state goes there.

Nothing on this path may block on a lock. One caller is the kernel's own
page-fault path, which arrives holding mmap_read_lock and may hold a
page-table lock; taking either again is a deadlock, not a slow path. Found by
doing it. That caller marks itself and is not inspected; the other only tries
for the lock, and UNKNOWN is an answer rather than a failure to give one.

=== b8709335b 2026-08-03
vmctx: the assisted syscall on 7.0.14, and a call that ends where any syscall ends

This tree carried the architecture in its working directory and never in a
commit: the monitor-driven syscall, the service context, the register change
mask, the per-page protection, and the signal ordering below. Every kernel this
project has measured on the AMD box since was built from an uncommitted working
tree, and src/ is not tracked by the repository that holds the userspace half,
so the only record of any of it was a directory nobody backs up. That is the
first thing fixed here.

What it brings, matching what linux-6.18.35 already carries as commits:

  - VMCTX_CTL_SYSCALL: the monitor supplies a number and arguments and the
    *context* performs the call, in its own address space, with its own
    descriptors and identity. A monitor may not make the call itself: it is a
    different process, the same address is different memory in each of them,
    and every pointer argument would be answered from the wrong memory.
  - VMCTX_CTL_ADOPT and the service context: a task that holds an address space
    and never executes. It needs no virtualisation backend, which is the whole
    point -- the machine that owns a program does not have to be able to run it.
  - the register change mask, including FSBASE and GSBASE, so a monitor learns
    what a call moved without reading the register set twice and diffing it
    across a machine boundary.
  - vmctx_mprotect() per page, so a protection applies to the pages that exist
    rather than failing on the first hole.

And the one thing this tree has that 6.18.35 does not:

A syscall does not end at the handler's return statement. What follows it on the
way back to user mode is the rest of the ABI -- a pending signal is delivered as
a frame pushed onto the program's own stack with the frame pointed at the
handler, and -ERESTARTSYS becomes either a rewind onto the SYSCALL instruction
or -EINTR. All of it is expressed as changes to one pt_regs, which is exactly
what a monitor is handed back.

That work was already happening. It happened one iteration later, in
__exit_to_user_mode_loop(), after the registers had been snapshotted and the
monitor woken with them -- and the next forwarded call's SETREGS overwrote the
result. Measured on tests/sig1.c: after the guest's raise(3) the service context
stood at rip 0x402070, the program's own SIGUSR1 handler, with a complete signal
frame written into the program's stack at rsp 0x7fffffffe2f8, while the machine
running the program carried on from the instruction after its SYSCALL, never
entered the handler, and died in __printf_buffer with the frame sitting in
memory it believed was free. Ten runs out of ten.

So vmctx_do_monitor_syscall() runs that work itself, before it reports. Nothing
here is specific to signals and nothing decides anything: it is the
architecture's own return-to-user code, one step earlier, so the frame it leaves
is the frame the monitor reports. The machine executing the instructions enters
the handler knowing nothing about signals, which is the rule the design is built
on.

The other half is when there is no call to end. A signal is delivered at an
instruction boundary, and a service context is never where the program is except
while a forwarded call is in progress; everywhere else its frame is the leftover
of whatever call it last made. So __exit_to_user_mode_loop() holds such a signal
back and the park became killable, because an interruptible wait returns the
instant TIF_SIGPENDING is set and would spin.

Only a signal that has somewhere to go is held. Holding the others is not a
deferral but a refusal, and tests/pf3.c said so at once -- three children that
had earned a SIGSEGV reporting "exited 242 rather than dying".

sig1 goes from 0/10 to 12/12. Independently re-measured over three full suite
rounds: 60 passed, 3 failed, and the three are the pg2/pg3/th9-static coherence
family that was flaky before this and is not touched by it.

=== c5b9ccd7b 2026-08-03
vmctx: hand a page over from the address space, not from one context

VMCTX_CTL_TAKE works on one context: it pins the page, zaps that one VMA, and
copies the bytes afterwards out of the pinned page. A guest address space on the
destination is one backing object mapped MAP_SHARED into several contexts, each
with page tables of its own, so everything that would make that copy safe is
missing. The other contexts still map the same physical page and are not
stopped, so the bytes change under the copy; nothing removes the page from the
object, so any of them can fault it straight back in; and the TLB flush that
comes with the zap reaches only that one mm, so a sibling's vCPU keeps a
translation to a page it has been told it lost. Userspace then issues one of
these per context and punches the object separately, which turns a single
hand-over into a sequence with a gap at every join.

None of those gaps can be closed from above, because each is a window inside an
operation userspace cannot enter. Measured: a userspace attempt to fix the same
race by reading the object after every context had let go made it worse, 8 tears
across twelve runs becoming 20, because it widened the window it meant to close.

So the hand-over becomes one operation. Under the object's folio lock -- which
is what a fault on that offset blocks on in shmem_fault(), so no context can
acquire the page while this runs -- unmap_mapping_range() removes it from every
mm that has it, with each mm's own TLB flush rather than one mm's; the bytes are
copied with no mapping left anywhere and every would-be faulter parked; and
shmem_truncate_range() removes it from the object, so this side can no longer
answer for it.

One window is left and is named rather than hidden: the folio lock has to be
dropped before shmem_truncate_range(), which takes it itself, and a context
woken in that gap can map the page and write it before the truncate discards the
write. Two calls wide, against a userspace loop and a separate punch.

-ENOENT for a range that is not object-backed, and for a large folio, whose
removal would take memory the caller never asked about. The caller falls back to
the per-context path, which for those is no worse than before.

Measured on tests/pg2.c, which writes one page from both machines at once:
tears went 8 across twelve runs, to 1 across twelve, to 0 across eight, with 344
to 616 hand-overs per run taking the atomic path and one falling back. pg2's
other failure, the one it calls bad payloads, is unchanged by this and is not
explained by it.

Also recorded, in mm/memory.c: the fault hook's exclusion of VM_SHARED is
correct, and the obvious suspicion that it starves a guest of its own memory is
wrong. An instrument there fired zero times across four pg2 runs, three of them
failing, against a control of 153 other vmctx messages reaching dmesg in the
same runs. A guest's memory faults never reach the host fault path at all: its
instructions run in a hardware guest, so a missing page is a nested page fault
taken as a VMEXIT and handled by the backend.

=== 0d12bdf2f 2026-08-03
vmctx: a page may not change machines while anything here can still reach it

Removing a page's page tables is not the same as removing every way to reach
it, and both hand-over paths treated them as the same thing.

A syscall this side performs pins its buffers with get_user_pages() and holds a
struct page reference for the whole call. A driver may hold a kernel mapping. A
device may already have the physical address in a descriptor. None of that is
undone by a zap or by unmap_mapping_range(), which walk page tables and nothing
else. So a page handed to the other machine while any of it is outstanding is a
page this machine can still write -- after the other machine has been told it
owns it and has begun writing it too.

Concretely: the program reads from disk into a buffer, the call blocks on the
device, and while it is blocked the other machine claims the buffer's page to
write. The read completes and the driver writes into memory that now belongs to
the other side, which is never told. Nothing in the page tables records that
this is possible, and no test in this tree would see it.

The kernel tracks all of it already, so vmctx_folio_may_move() asks instead of
assuming: writeback is waited for, because it ends by itself; a DMA pin
(FOLL_PIN) is refused, because it means precisely "a device may write this"; a
page still mapped after the unmap is refused; and a reference count above what
the page cache and its mappings account for is refused, which is what catches
the get_user_pages() reference of a call that has not returned. It is the same
comparison the migration code makes, for the same reason.

Both paths use it: vmctx_ctl_take(), which is how a monitor gives a page back to
the machine running the program and therefore where a pinned buffer would be
handed away, and vmctx_ctl_takeobj().

-EBUSY is not a failure. It says the page cannot move *yet*, and the caller is
meant to wait and ask again. That is the escalation lock this design needs,
stated where the facts are rather than inferred in userspace from syscall
boundaries -- an earlier attempt at the latter was both too coarse to be usable
and blind to every case above.

NOT YET WIRED UP, and not yet run. The callers still read a negative answer as
"this path will not work" and fall back, which for -EBUSY is wrong: they must
wait for the page and retry. Committed at this point because the guard is
conservative -- it refuses hand-overs that used to be made unsafely, and cannot
make one that was safe unsafe -- and because the analysis belongs with the code
rather than in a conversation. Compiles; no kernel built from it has been
booted.

=== 74889415f 2026-08-03
vmctx: claim a page by freezing it, not by deciding it looks free

folio_ref_freeze() sets a folio's reference count to zero if and only if it is
exactly what was expected, atomically, and fails if anyone else holds one. That
is how this kernel takes exclusive ownership of a page; mm/migrate.c freezes
before it moves a folio and answers -EAGAIN when the freeze fails.

What was here instead read the count, compared it, returned, and let the caller
copy afterwards -- the same question with a window after it, in which any
reference could be taken. Even with a correct count that was never a claim.

The count to expect is what the page cache and mappings account for, plus the
references this caller holds, plus one. That last one is measured rather than
argued: the instrument that replaced the previous refusal reported refs=2
want=0(+1) for anonymous pages and refs=3 want=1(+1) for file-backed ones, on
every page, with no DMA pin, no leftover mapping and nothing on the LRU. A
constant off-by-one in both populations is an accounting error and not a holder,
which is why two earlier kernels refused nearly every hand-over and stalled the
system.

The freeze is held only across the copy; vmctx_folio_release() undoes it once
the bytes are out, because a frozen folio is one nothing may touch at all.

vmctx: the extra reference was the LRU-add batch, on somebody else's CPU

Freeze at the exact count the page cache and the mappings account for, plus
the caller's own references. Not one more.

Kernel #41 answered the question #38 and #40 could not, by failing the other
way: it froze at exact+1 and refused 391k hand-overs in one suite run (6
passed, 57 failed -- the #36/#38 stall reproduced), every refusal reading
refs=2 want=1(+1) mapcount=0 pinned=0 lru=1. Pages already on the LRU have an

an unreturned get_user_pages, an in-flight read): -EBUSY, the caller waits
and asks again, and nothing anywhere answers with bytes that are not the
page's. The instrument stays, and now discriminates: an lru=0 refusal after a
drain-all is a new fact, not the batch.

=== 2e945a649 2026-08-11
vmctx: the hand-over is atomic under contention -- the lock is the exclusion, not a freeze

vmctx_ctl_takeobj() froze the folio (folio_ref_freeze via vmctx_folio_claim)
after unmapping it, to prove no one could write it during the copy. Under
multi-context contention that freeze is a LIVELOCK: a faulter reaches the folio
through __filemap_get_folio, takes a speculative page-cache reference, and only
then blocks on the folio lock -- so with four contexts faulting one page the
reference count is never the expected value, folio_ref_freeze never succeeds,
TAKEOBJ returns -EBUSY for ever, and userspace falls back to the per-context
take, which splits the address space (some contexts lose the page, some keep
it). tests/hx1.c is exactly that: four threads writing their own words in one
page while a forwarded read keeps wanting it, and a thread reads its own store
back thousands of rounds stale.

The freeze is unnecessary here. This path holds the folio lock across
everything, and unmap_mapping_range() under i_mmap_rwsem removes every mapping
in every mm; after it no CPU has a PTE and none can make one, because a fault
for this offset blocks in shmem_fault() on the lock we hold. References held by
those blocked faulters are harmless -- a reference is not a mapping, and only a
mapping can write. The LOCK is the exclusion.

The one writer the lock does not stop is a device holding a DMA pin, which is a
refcount not a mapping and survives the unmap. So folio_maybe_dma_pinned() is
checked twice: once before the unmap as a cheap early-out, and once after --
the check that counts, at the last instant a pin can exist, since once the PTEs
are gone GUP-fast finds none and GUP-slow blocks on the lock. folio_mapped()==0
is asserted there too; a non-zero value would mean the invariant is gone, so it
refuses rather than copy a page something can still write.

Measured: suite 75 passed / 0 failed (isolated: this kernel change alone, with
userspace unchanged), vmctx_takeobj_lost stays 0, and the four-context livelock
is gone. The per-context fallback no longer runs for hx1's page.

=== b5c1464d6 2026-08-13
vmctx: a forwarded syscall's write-hold ends on a block, not a timer

held for the rest of the window and ping-pongs.

=== afbc920c3 2026-08-16
vmctx: do the exit path's write to guest memory while the context is still in the protocol

## Why that write cannot be wrong natively, which is exactly why it breaks here

mm_release() -- do_exit -> exit_mm -> exit_mm_release -- performs
put_user(0, tsk->clear_child_tid) and a FUTEX_WAKE. That is the
CLONE_CHILD_CLEARTID contract, the thing that makes pthread_join() return.

Three properties make it safe on an ordinary kernel, and they are worth naming
because the third is what vmctx breaks:

  1. current->mm is STILL INSTALLED. exit_mm_release() is the first statement of
     exit_mm(), before task_lock(current); current->mm = NULL; mmput(mm). The
     page tables are live and CR3 is that address space.
  2. mm_users > 1 is tested first, so there is another thread that can still
     observe the word; with no other user there is nobody to tell.
  3. put_user is an ordinary user access. A page that is not present simply
     FAULTS IN through handle_mm_fault() on the one true address space, and the
     store lands; a genuinely bad pointer takes the uaccess fixup and returns
     -EFAULT, which the caller deliberately ignores.

So the write is GUARANTEED to succeed. Natively that guarantee is harmless --
there is only one copy of the memory, so "find or make a page" can only find
the right one.

## Under vmctx the guarantee is the hazard

The address may be owned by the other machine, and by the time mm_release() runs
this code has already let go: vmctx_task_exit() is called at do_exit()'s top
(exit.c:915) and exit_mm() is fifty lines below it (:969), so current->vmctx is
NULL and vmctx_mm_forget() has run. Every guard is keyed on one of those two --
vmctx_anon_fault on current->vmctx, vmctx_foreign_anon_fault on the mm not being
current's, the fault accounting on the mm being registered -- so none fires, and
do_anonymous_page() does what it is guaranteed to do: it MAKES a page. The store
lands in memory nobody asked for, both machines then hold that address, and they
disagree -- the source reads 0 while the guest's copy still holds the old tid. A
joiner reading through the protocol is told nothing has changed. That is the
"both machines are holding it" the source's own ownership sweep reports.

## The fix

Do it at the top of vmctx_finish(), where current->vmctx is still set and the
monitor is still attached: put_user's fault is redirected like any other, the
page is fetched from whichever machine holds it, and the zero lands in the
guest's real page. Then clear t->clear_child_tid so mm_release() finds nothing
to do and cannot repeat the write outside the protocol. mm_users > 1 is kept
from mm_release rather than reasoned about again.

The wake stays, and that is not incidental: suppressing the exit path's write
WITHOUT doing it here was measured and was worse, because the futex key for
anonymous memory is (mm, address) and not the physical page -- the exit path's
wake reached waiters even when its store went to an invented page. This moves
both halves inside the protocol instead of deleting the half that worked.

Measured, ws1 x40: the in-band write fires 158 times (four per run, one per
thread) with 2 put_user failures. ws1 is 37 pass / 3 fail, unchanged from the
previous step -- so this closes a real hole without moving the remaining rate.
15% at the start of this work, 7.5% now, and the lost-write mode is gone.

vmctx: a context waiting for its monitor must not hold mmap_lock

## The deadlock, photographed

With the fault deadline turned off so the hang holds still, ws1 wedged with:

  ctx A (a service context)  faulted inside a forwarded syscall;
      handle_mm_fault holds mmap_READ_lock and sleeps in vmctx_report.
  vmhome                     serving exactly that fault with a POKE:
      access_process_vm -> __access_remote_vm -> wants mmap_READ_lock.
  ctx B (main)               in mmap(NULL, 0x801000, ...) for a pthread stack
      -> queued for mmap_WRITE_lock.

rwsem is fair, so the monitor's NEW reader queues behind the pending writer; the
writer waits for the reader asleep in vmctx_report; that reader waits for the
monitor. A three-way cycle on mmap_lock, needing only a thread creation to
overlap another thread's faulting forwarded syscall -- ws1 exactly, and browsers
constantly. Nothing is corrupt, which is why every content check in this tree
reported a clean zero.

## The fix, and the three rules it obeys

Drop the lock and return VM_FAULT_RETRY, exactly as handle_userfault() does for
the same reason. From its own account of the rules:

 - only with FAULT_FLAG_ALLOW_RETRY; without it the caller cannot cope with a
   dropped lock, so the old blocking path stays;
 - with FAULT_FLAG_RETRY_NOWAIT, return VM_FAULT_RETRY *without* dropping and
   without sleeping;
 - once dropped, the answer MUST be VM_FAULT_RETRY -- returning VM_FAULT_SIGBUS
   there would have the caller unlock a lock this function already released.

No lost wakeup: the event is not published until vmctx_report(), which runs
after the drop, so nothing can answer in the window; and the wait is a
wait_event on reply_wq, which re-tests reply_pending after
prepare_to_wait_event(). Nothing of vmf survives the drop -- the address and the
write bit are copied out first, because another thread may munmap the range and
free the VMA; a range genuinely unmapped by then makes the retry fault on
nothing and the program earns its SIGSEGV, which is correct and is what
userfaultfd gives. Forward progress is bounded: the retry arrives with
FAULT_FLAG_TRIED and takes the blocking path, so this loops at most once.
in_mm_fault is cleared on this path because the lock really is no longer held.

of them acting together:

  load-bearing from kernel #43's futex starvation, but that failure
  was the LIFETIME's (a fixed TTL holding through a block), not the
  coverage's.

  directions at once: too short and an actively-running call has its
  page stolen mid-copy (the defect above); too long and a call that
  has BLOCKED -- futex_wait asleep, a pipe read with no data -- pins a
  page its own waker needs, which is the #43 deadlock.

touched, or could touch, is held exactly while the call could touch it
again: while its thread is running the call, or parked in vmctx
waiting for one of the call's own faults to be served (ev_pending).

be touching anything, so every hold lifts; when it wakes and touches
again, the touch faults (absent now) or is re-covered by presence.

   reached the old attach -- is precisely the task whose mm the

the userspace side; what remains of mremap handling there is the one
thing only the call can express, the old-to-new relocation pairing.

=== b34ea6de3 2026-08-20
vmctx: MADV_DONTNEED is a discard, and the change log now says so -- soft entries drop pages, not mappings

The mm change log (the previous patch) covers every way a MAPPING dies,
because MMU_NOTIFY_UNMAP fires wherever one does. MADV_DONTNEED is the
mutation that arm structurally cannot see: it raises MMU_NOTIFY_CLEAR,
and CLEAR cannot be logged wholesale -- it also fires for page
migration and for the coherence layer's own COW write-protects, where
the mapping and its content both live on and "forget this range" would
be wrong.

But DONTNEED is a contract with content: the next read of a private
anonymous range observes fresh zero-fill, and glibc's allocator leans
on exactly that when it trims arenas -- memory handed back by DONTNEED
is treated as zeroed when next carved up. A machine still serving the
old bytes is not slow, it is wrong, and the wrongness surfaces as heap
corruption far from the madvise. Measured (tests/md1): under a guest,
a DONTNEEDed arena read back its 0xaa fill from the destination's
untouched copies.

So the discard gets its own note, from the one call site that MEANS
discard: mm/madvise.c's MADV_DONTNEED dispatch (DONTNEED_LOCKED
included, MADV_FREE excluded -- FREE's lazy semantics permit the old
bytes until the next store, so propagating it would be optional
correctness). The report still comes from where the memory is
released, never from decoding a syscall number in userspace; a
quick-out on vmctx_mm_live keeps the slot scan off boxes with no
context running.

A discard is a SOFT entry -- bit 0 of the stored start, which page
alignment leaves free -- because the consumer must do a different
thing: ownership resets and every content copy dies, exactly as for an
unmap, but the mapping and its records live on. The monitor forgets
page ownership only (a RELRO seal and a shared-file range describe the
mapping, which is untouched) and ships the flag through the reply; the
destination punches its object and retained copies and applies the new
VMCTX_MAP_ZAP to every member of the address space: drop the PAGES of
the range and keep the VMAs, implemented as do_madvise(MADV_DONTNEED)
on the member's own mm -- the operation IS a dontneed, with its own
locking and cross-mm form, so it is used rather than reimplemented.
The next touch faults through the ordinary service and fetches the
fresh content from the machine that owns the program: zero-fill for
private anonymous, the file's bytes for a file mapping, which is why
the destination never manufactures zeros itself (a DECLINE that
invents zeros is the recorded evil).

The consecutive-duplicate suppressor compares flag and range together,
so a hard and a soft event on one range never collapse into each
other.

=== edec3e4c6 2026-08-24
vmctx: the change log stamps its events itself -- a drain-time stamp cannot order them

The monitor stamped vacated ranges when it DRAINED them, and a drain is a
userspace race: the log is per mm and any connection's forwarded call
drains it, so two threads pop concurrently and the later stamp lands on
the earlier event. A recycled range's stale vacate then outranks the mmap
that superseded it, and the destination -- whose skip rule is exactly
"a vacate never touches a construction stamped newer" -- legally punches
the live mapping. Photographed on netsurf's font scan (session 42):
munmap, re-mmap of the next font into the same hole, the old vacate
spilled onto a later reply stamped fresher than the new mapping's
construction, the fresh VMA unmapped in every member, and the first read
of the font's magic answered -14 -- exit 242, main parked in futex for
the worker that died, the 10x10 stub window forever.

So the hook stamps each event at the moment it logs it, under the log's
own lock -- the only place that knows the true order of an address
space's mutations. VMCTX_CTL_MMLOG hands the stamp out per entry, and
returns cur, the counter at the drain read under the same lock: the
reply's constructions carry cur, every event logged before that instant
has a smaller seq, and a construction's address is unpublished until its
reply, so no event that outranks it can precede the sample. The
userspace counter is gone; only "later than" was ever asked of it, and
now the kernel answers.
