# Firefox audit — work in progress

Objective: correct, sustained cross-machine Firefox for everyday browsing and
interaction, with performance compared against native execution. The user
requested a complete line-by-line audit and authorized kernel changes.

This is an ongoing audit, not a claim of completion. `read-ledger.json` records
the initial source identities and explicitly reviewed ranges. Upstream sources
under `src/` are dependencies; both kernels' project changes and the surrounding
upstream mechanisms are part of the architecture review.

## Evaluation order

1. Read all project code and both kernels' modifications, tracking coverage.
2. Establish reproducible ownership and lifecycle checks, then isolated browser
   runs that verify rendered content and real input handling.
3. Reproduce each suspected failure before fixing it; preserve failure artifacts.
4. Run targeted controls, regression suites and cross-machine checks after each
   change. Kernel builds require booted validation before performance claims.
5. Alternate native/guest runs with the same Firefox, profile settings, content,
   display and workload. Report startup, navigation and interaction latency,
   stability, page transfers and syscall costs. Distinguish different CPU speeds.

## Initial findings (repair status recorded below)

- `pgstate.h`: fixed 8192-slot table silently loses state on exhaustion while
  callers still report successful claims. Reproduced: two simultaneous claims
  succeed for the 8193rd distinct live page in `ownership.c capacity`.
- `pg_yield_to_source`: a failed claimant resets the incumbent's transient to
  INVALID. Reproduced with `ownership.c exclusion`. Callers also proceed after
  claim timeouts; fixing this needs a coherent transaction/lifetime treatment.
- `own.h` and `pgstate.h`: power-of-two tables hash byte addresses directly;
  page alignment removes low hash entropy. `retain_slot` needs the same review.
- `own.h`: the key was hashed before page normalization. `ownership.c normalize`
  reproduced duplicate claims for addresses naming the same page. The current
  isolated edit normalizes first and hashes the page number. Normalization now
  passes. Alternating standalone runs measured median 4.865 us per ownership
  transition before, 0.253 us after (32768 pages, four passes). This measures
  only table operations, not browser speed. Header staged on AMD; deployed
  production binaries have not yet been rebuilt.
- Browser harnesses include broad process kills, stale-output paths and window
  oracles that do not establish successful content rendering or interaction.
- Userspace Makefile fingerprints all sources but its dependency rule excludes
  `own.h` and `pgstate.h`; the fingerprint alone does not force relinking.

None of these findings is yet attributed as the cause of Firefox's failures.

## Destination loan records

The local destination change replaces the packed-key/open-addressed loan
array with chained records keyed by full address-space id and normalized page.
The bucket array no longer caps live records or stops a lookup after 64 probes.
Unmapping frees the matching records without hiding neighbors. Scans copy
record values under the loan mutex before dropping it; they never retain live
node pointers across page operations. Allocation failures terminate instead of
silently losing a loan or omitting records from a scan. This corrects record
storage; it does not supply transaction or address-space incarnation semantics
missing elsewhere in the protocol.

`control/page-tables.c` reproduces the old deletion and truncated-id failures,
128 colliding records with normalized offsets, loss beyond capacity, concurrent
mutations in four colliding address spaces, and unrecorded allocation failure.

records and stops on snapshot allocation failure. Address/undefined/leak

sandbox; the checks were rerun successfully outside it. Logs are in ignored
`logs/audit-20260906/loans-host-ab.json`, `loans-asan.json`, and

## Fork extended-state control

`control/fork-state.c` sets XMM15 to a 128-bit sentinel and changes MXCSR's
rounding mode immediately before a raw fork syscall. Both branches capture the
registers immediately after the syscall, before libc can modify them. The
parent checks its own state and the child's actual wait status. Ten local
native runs passed; a native run on AMD passed as well.

On AMD loopback with `exclusion-bin`, the parent retained the sentinel and
rounding mode, but the child received an all-zero XMM15 and the original
rounding mode (`0x1fa0` instead of `0x7fa0`). The guest exited 1. This is a
reproduced architectural failure, independent of the Firefox timing workload.
`runany.sh` returned harness status 0 despite the guest failure, as its contract
permits; the guest output and destination exit record are what grade this test.
Evidence: ignored `fork-state-native.json` and `audit-fork-state-1/`.
Five further alternating AMD native/loopback pairs reproduced the same result
in every pair: all native checks passed and all guest children lost the state.
Module references stayed zero and mm_live stayed 28 before/after the sequence.
The result and each run's logs are in AMD/local `fork-state-repeat/`.

The destination creates a new monitor-derived task for a guest fork and
supplies GPRs without extended state. Upstream `fpu_clone` correctly copies the
actual calling task's registers; here that caller is the monitor. A repair must
cover initial entry, fork/clone, exec, signal delivery/return and supported
cross-machine CPU features. Copying only these two tested registers would not
satisfy that contract.

## Partial permission change control

`control/mprotect-gap.c` creates three writable pages, unmaps the middle one,
then requests read-only protection over all three. Linux changes the first VMA
before discovering the hole and returning ENOMEM. The control requires a
SIGSEGV/SEGV_ACCERR at the first page on a subsequent write, and also checks
that the last page remains writable. Five local native controls and an AMD
native run passed.

With `installed-bin` on AMD, the guest's first-page write succeeded (fault=0),
and the guest exited 1. `reply_note_map` ignores failed mprotect calls; no
permission update reaches an already writable destination PTE. Both kernel
versions' actual mprotect loops confirm the partial-change behavior. Preserved
controls/logs: ignored `mprotect-gap-native.json` and `audit-mprotect-gap-1/`.
The module reference count returned to zero and mm_live stayed 28. This is an
open architectural defect: replicating a syscall's requested range only on
success cannot reproduce the source's actual mapping changes.

## Failed fork cleanup control

`control/fork-failure.c` asks a service context to perform clone3 with
CLONE_PIDFD and an invalid pidfd output address. The native call first confirms
EFAULT. The same assisted call returns EFAULT successfully, but the child has
already acquired a vmctx record before the output copy fails. It never runs
and therefore never reaches the do_exit hook that normally retires the record.
One controlled attempt on AMD kernel #181 measured mm_live
28 (before), 29 (service), 30 (after the rejected clone), 29 (after killing and
reaping the service). The remaining record is a reproduced leak; the new test
intentionally performs only one failed fork on an unfixed kernel.

Both kernel/fork.c working trees now call vmctx_task_exit on the rejected
child before exit_thread/mmput in the fork error path. A vmctx_copy_task error
also takes that path so architecture resources created by copy_thread are
released. Baseline hardware evidence is in ignored `fork-failure-before.json`.
The repair is pending kernel-build and hardware validation. Both exported
kernel directories carry a working-tree 0002 patch preserving the change.

The Intel fork object compiles with the change. The isolated AMD copy matches
the original fork/core source hashes before applying it; its planned release
is `7.0.14-vmctx-audit-fork1`. No kernel or boot file has been replaced. Its first
two build attempts failed in native exec during configuration. The second was
traced: native sh processes 404693 and 405717 received E2BIG from execve. Kernel
messages identify those same tasks as third-party writers to a context whose
record has monitor id 401447. The leaked mm record retains a raw pointer with
no mm lifetime reference; reuse can therefore attach its policy to an unrelated
native mm. This is host interference, not merely an inaccurate diagnostic count.

Kernel/module counters, all task stat/status/wchan snapshots, complete dmesg,

## Signal extended-state control

The new `control/signal-state.c` brackets a raw self-signal syscall with SIMD
and MXCSR snapshots. Its assembly handler checks the signal-entry state,
changes it, then lets the real sigreturn restore the interrupted state. Ten
local native runs passed both entry initialization and return restoration.
AMD guest validation is pending recovery. This extends the fork-state control
to a separate architectural boundary; it does not implement state migration.
