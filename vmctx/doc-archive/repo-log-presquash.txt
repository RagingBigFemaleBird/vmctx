=== aaf5793 2026-07-27
lan-boot: run a program on one machine using another machine's resources

A netboot lab and the software that proves a single idea: a process's
execution can be separated from everything its execution needs. A browser
installed only on machine A runs on machine B — its code and memory
resident there, its instructions executing on that CPU — while every
syscall it makes is executed back on A, and its rendered output appears on
A. Byte-identical to running it locally, at 99.9% of native compute speed.

Verified on real hardware throughout, on both vendors: AMD Ryzen 7 4800H
(SVM) and Intel Core i7-7700K (VMX). Nothing here was tested in emulation.

WHAT IS HERE

  start.sh, stop.sh, config/     a PXE boot server: dnsmasq in proxy-DHCP
                                 mode (the site's own DHCP keeps handing out
                                 addresses), its built-in TFTP serving iPXE,
                                 and an HTTP server for kernel, initramfs,
                                 modloop and a partial Alpine package mirror.
                                 Nothing on the LAN needs reconfiguring.
  config/embed.ipxe              embedded in all three iPXE loaders so a
                                 client finds the boot script without
                                 depending on what the site's DHCP says
  tools/build-kernel.sh          builds the kernel in src/linux-6.18.35 and
                                 stages vmlinuz/initramfs/modloop for boot
  tools/mirror-apks.py           mirrors a dependency closure of Alpine main
  vmctx/kernel/                  the hardware backend: AMD SVM and Intel VMX
  vmctx/user/                    the tools, ~6300 lines of C
  vmctx/README.md                the full record: what was built, what was
                                 measured, and what was got wrong on the way
  vmctx/OBJECTIVE.md             the standing goal and its status
  avm.md                         the original objectives

THE TOOLS

  dumpvm       what this CPU can do and whether a backend is registered
  vmselftest   SVM guest entry in a sandbox: enter, write memory, exit
  startvm      run a program in-guest on this machine
  vmenter      the minimal case: user code as a guest, one forwarded write
  vmcat, vmproc, vmthreads     targeted tests of paging, processes, threads
  vmmon        a monitor process servicing another context's events
  vmmig        checkpoint a running context and resume it elsewhere
  vmhome       serves a program's memory and executes its syscalls
  vmremote     runs the guest on this machine against a remote vmhome
  vmbench      the same binary natively and in-guest, so "near-native" is
               measured rather than asserted
  remote-run.sh   does the whole thing end to end and checksums both ends

HOW REMOTE EXECUTION WORKS

Home runs vmhome. It starts the program under ptrace and stops it at its
entry point, so the *home* kernel does all the ELF work — interpreter,
libraries, relocations, the initial stack with argv and auxv — and the other
machine never has to understand any of it. That stopped process is the
oracle: the authoritative copy of the program's memory.

The remote machine runs vmremote, a monitor over vmctx_ctl(2). It maps the
shape of the oracle's address space — addresses and sizes, not one byte of
content — and enters the guest. Every page the guest touches faults, is
fetched from home in chunks, and is installed. Syscalls come back out as
#UD (the guest runs with EFER.SCE clear, so SYSCALL raises it) and are
forwarded home, except those that must run where the task lives: mmap and
friends, signal state, clone, futex, wait4, the per-task registrations.

At home each context has a shadow: a process whose address space mirrors the
guest's through userfaultfd. Forwarded syscalls execute in the shadow, so
pointer arguments resolve by faulting the guest's pages across the network
and whatever the kernel writes is pushed back. Nothing in vmhome knows what
any particular syscall does. When the guest forks, the shadow forks at that
instant — it must inherit exactly the descriptors the child will use.

WHAT WAS BUILT, IN ORDER

Detection and bring-up; a guest entered and left cleanly; real user code as
a guest with one syscall forwarded; guest registers marshalled so real
arguments pass; generic dispatch and demand paging; fork, exec, signals and
threads; a monitor process servicing another context; checkpoint and
restore; syscalls forwarded to another machine; memory served from another
machine; a program that exists only on the far side; a browser; a browser
fetching over HTTP; and the whole of it again on Intel.

THE BUGS WORTH KEEPING

Most of the work was diagnosis. These are the ones whose symptoms pointed
somewhere other than their cause.

Transparent huge pages defeat demand paging. A 2 MiB THP satisfied the
first touch with 2 MiB of zeros, and the guest ran blank memory that had
never been fetched.

Absent pages must be answered as absent, not as zeros. Handing back a zero
page for memory that does not exist yet means the guest never faults there
again and runs whatever it invented.

The shadow's descriptors shared the guest's numbering. The guest allocates
its descriptors through its own forwarded syscalls, so it is free to close
or dup2 over any number — and a forked child that closes everything above 2
shuts the shadow's socket, its userfaultfd and its page channel. They live
at 900+ now.

The guest cannot run on mm->pgd when page-table isolation is on. PTI marks
the user half of the kernel-side PGD no-execute, so the guest cannot fetch
its own first instruction: it faults on its entry point with the page
present, the access user-mode, and the fetch bit set. Invisible on AMD,
which does not turn PTI on. The first fix for it did nothing, because it
was guarded on CONFIG_PAGE_TABLE_ISOLATION and the symbol had been renamed
in 6.12 — an #ifdef on a renamed symbol deletes the code in silence.

HOST_FS_BASE must be maintained by hand on VMX. VM exit reloads the host's
FS base from that field, and FS base is where the task's user TLS pointer
lives while it is in the kernel. Written once at setup, it silently reverted
the running task's TLS on every exit: the program set it with arch_prctl,
had it undone by its own next exit, and died reading %fs:0x0. SVM never
shows this — VMSAVE/VMLOAD do it for free.

CPUID exits unconditionally on VMX and had to be emulated. The dynamic
loader asks before it resolves a single ifunc.

A read lock leaked on every fault that had to wait. The fault path called
fixup_user_fault() and unlocked only when it had *not* set *unlocked, which
is exactly backwards: that function never returns with the lock dropped,
and the flag means the lock was released at some point so the caller's VMA
pointers are stale. The task then carried a stray reader, and the next
guest munmap or mmap blocked against a lock it held itself — forever, with
no second party, and nothing in any log. sysrq-w showing exactly one blocked
task and no other waiter is what named it: a deadlock with one participant
can only be a task against itself. It is also why the machines became
unresponsive afterwards, since a leaked reader blocks anything that walks
/proc for that task.

One mutex held across a blocking syscall deadlocks a forked guest. The
shadow call lock was global and held for the whole round trip, and the round
trip contains whatever blocking syscall the guest asked for — so a parent in
select() starved its own child, which therefore never wrote the bytes the
parent was waiting for. Removing it took the forking case from fifteen
seconds to three.

A mirror that never forgot. Regions were mapped once and considered covered
forever, but guests unmap memory and mmap something else at the same
address; the pages from the old mapping stayed, and a syscall reading
through a pointer into the new one got bytes from a previous life.

A client must not build a URL from a field it was never sent. A second
machine PXE-booted, completed proxy-DHCP with the right server, and stopped
with "DNS name does not exist" — because the reply carried no next-server,
so the boot script produced "http://:8080/boot.ipxe", a URL with no host,
and iPXE dutifully tried to resolve the empty name.

TWO LESSONS THAT COST HOURS EACH

Stale binaries produce false results. A test whose binary silently failed to
copy — Text file busy, ssh still exit 0 — was reported as a fix. Everything
is checksummed on both ends now and refuses to run otherwise.

A timeout does not mean the guest hung. The monitor has outlived its guest
more than once. Check for OP_FINISH in home's log before concluding
anything.

MEASURED

  in-guest syscall        0.64 us against 0.16 us native — the VM-exit

  browser, file render    ~0.5 s guest runtime, both machines
  browser, over HTTP      ~2.6 s by IP, ~2.9 s by name (which forks)
  correctness             40/40 byte-identical across links and w3m on both
                          targets; elinks 8/8 and 6/6 cross-machine

=== ef64055 2026-07-27
vmctx: make the remote browser four times quicker, and stop it dying at random

  links -dump http://localhost:8080/, browser on home, target executing
    ~2.9 s  ->  0.65 s        byte-identical to native, 28/28 over the LAN

  in-guest syscall            0.64 us  ->  0.42 us      (native 0.16 us)
  forwarded syscall time      0.563 s  ->  0.263 s      (median of ten)
  Intel, both ends on one machine, elinks:  10 failures in 10  ->  0 in 20

Four costs and one long-standing corruption, each found by measuring rather
than reasoning, because every previous guess about where the time went had
been wrong.

## Measuring underneath the network

local-run.sh is remote-run.sh with the syscall side moved onto the target, so
both ends talk over that machine's loopback. Over the LAN a round trip is
~500 us and every cost inside vmremote and vmhome hides beneath it; at ~30 us
what is left is the work itself. Both wins below came from there, and neither
was visible any other way.

Three harness defects had to go first, or it measured nothing:

* `pkill -x vmhome` kills nothing on the target. busybox's -x compares the
  whole command line rather than the name, so it matched no process, reported
  success, and left the old vmhome holding port 9999. The next vmhome then
  failed to bind and died, and the run talked to the previous one — whose
  oracle was gone — which looks exactly like a guest that crashes early.
* SIGTERM is not enough. A shadow parked in a userfaultfd fault sleeps
  TASK_KILLABLE, which wakes for SIGKILL and nothing else.
* vmhome's listening socket is now close-on-exec. The oracle is vmhome forked
  and exec'd into the guest's program, so without it the oracle held the port
  for as long as it lived — outlasting vmhome whenever vmhome was killed. The
  process holding the port is named after the guest's program, so ps does not
  show what is wrong.

## Leaving the guest

The VMX backend released its VMCS after every entry — VMCLEAR, then VMPTRLD
and VMLAUNCH on the next. That was justified with a measurement showing it
cost nothing, but the measurement was of a run where every syscall was a
network round trip, which is to say it measured the network. Locally it was a
third of the exit cost: keeping the VMCS current and resuming took the in-guest
syscall from 0.64 us to 0.46 us.

Then the VMCS accesses themselves. Seventeen per exit, about seven of which
carried nothing. Three written fields never change between entries — CR3 moves
on exec, the two TLS bases on arch_prctl — and are now written only when they
differ. Three exit-information fields were read after every exit regardless of
what the exit was, and mean nothing for the exit that happens most, an external
interrupt. The reason is read first now, then only the fields that reason gives
meaning to. 0.46 us to 0.42 us; compute untouched at 248 Miter/s, as it should
be, since none of this is on the path where the guest runs.

## Giving a page back

After a forwarded syscall the shadow returns the bytes the kernel wrote, and
only those: a whole-page write-back would also carry the bytes fetched earlier
and undo whatever the guest wrote elsewhere in that page. But it sent one
request per run of changed bytes and waited for each reply, and a kernel's
writes into a page are not one run — a struct with untouched padding, or a
buffer whose new bytes happen to match the old ones, breaks into a dozen or
more. Measured: 248 pages went back as 3850 requests, fifteen round trips per
page averaging 49 bytes, the largest single cost in a forwarded syscall.

VMR_PG_PUTV carries every run of one page in one message — the same bytes,
chosen the same way, so the lock-word case the diffing exists to prevent is
untouched — and the receiver applies them with one process_vm_writev. 3847
runs now cost 230 round trips.

## The guest's SSE registers are the task's own

A long-standing intermittent failure, previously recorded as "one unexplained
miss I could not reproduce". With both ends on one machine it happens ten times
in ten on the Intel box, which is what made it findable.

Neither the VMCS nor the VMCB carries FPU or SSE state. Whatever is in the CPU
when the guest is entered is what the guest gets. That is right for this design
— the guest is the process's user context, so its registers *are* the
process's — but only if the process's registers are the ones loaded. Between
two guest entries the context blocks waiting for its monitor, so it is
scheduled away and back; coming back, the kernel leaves the FPU registers
belonging to whoever ran in between and sets TIF_NEED_FPU_LOAD, meaning "this
task's registers are in memory, load them before returning to user". The guest
was entered before that ever happened.

musl finds it in the first few hundred instructions of a program. alloc_meta()
zeroes a new malloc record with one SSE store:

	pxor   %xmm0,%xmm0
	mov    %rax,ctx.avail_meta	<- this store page-faults
	movups %xmm0,(%r10)

A fault between the two leaves through the monitor, and on the way back xmm0
holds whatever the host left in it. The "zeroed" record comes back non-zero,
musl's own assertion catches it a few instructions later and executes hlt, and
it arrives as a guest #GP inside libc with a heap corrupted by nothing that
touched it.

Fixed as KVM does it: with preemption already disabled, load the task's
registers if the kernel says they are stale. Nothing is needed on the way out —
they are then live and owned by this task, so a context switch saves them and
the return to user mode keeps them, which is what "the guest is the process"
requires. Both backends: the gap is not vendor-specific, and AMD was getting
away with it rather than being right. It costs nothing measurable —
switch_fpu_return does work only when the flag says the registers are stale,
which in a loop that never blocks is never.

It looked like a race for a long time, and was not one. The observation that
should have ended that reading much earlier was there throughout: the corrupt
value was identical on every run — same address, same bytes. A race does not do
that.

## Instrumentation, kept because the distinction it draws is invisible without it

* vmhome reports where a forwarded syscall's time goes: in the call, in the
  pages it faulted, pushing them back, comparing them.
* vmremote accounts for teardown and for the time between guest events, and
  names any gap over 200 ms with what the guest did either side of it. That is
  what found a two-second stall which was neither fault nor syscall — a monitor
  reply that could not wake the context it was meant for, fixed in the kernel
  tree and described in README.md.
* VMREMOTE_ORACLE_DUMP asks the owning machine what it has at an address while
  the oracle is still alive; VMREMOTE_WATCH_WORD reports what a word holds and
  the guest rip when it changed. "The guest wrote this" and "we served this"
  are indistinguishable in a memory dump without them, and together they are
  what identified the instruction above.
* VMREMOTE_DEBUG hashes each chunk it installs — two runs can fault the same
  addresses in the same order and differ in what arrives.
* The module's #GP report includes the guest's registers and the memory they
  point at. A #GP on a hlt is an assertion failing, so the useful question is
  what it found, not where.

Also: home_call could leave an oversized payload sitting in the socket, after
which every reply was matched to the wrong request. The fault and page buffers
are per thread — the page service fills pages too, and a forked guest has a
service thread per context, so one static buffer let one thread's chunk be
written at another thread's address. vmremote no longer reports a negative
"guest/other": fault and syscall time are summed over contexts serviced in
parallel and can exceed the wall clock, so it says they overlapped. vmbench is
staged with the other tools, being what the near-native claim rests on.

The exported kernel patches are regenerated, and say how. The directory held
one patch, exported from a commit a later squash had removed from the kernel
repository: it described 65 changed lines of the 1312 that differ from vanilla,
its filename named a different change from the one inside it, and nothing said
so — a stale generated file looks exactly like a current one. It is now the two
commits that repository actually contains, with a note giving the command that
produces them.

The project is named. It presented itself as "LAN boot (PXE) server", which is
what the top-level directory started as and has not been the point for a long
while: the netboot lab is how a kernel gets onto a test machine, not the thing
being built. It is AVM — Application as a VM — after the avm.md spec it
implements, and the README now leads with what that means and what it does,
with the boot server below as the lab it is tested on. The netboot pieces keep
their own names: start.sh really does start the LAN-boot servers, and boot.ipxe
really does print "LAN boot" while netbooting.

=== 9c0f4de 2026-07-29
vmctx: give a guest's threads their own state, and make its memory coherent

A graphical browser is the first guest with real threads, and the first
half of this is one shape of bug: state that was correct while one serving
thread answered one context, and became shared the moment guest threads
got contexts of their own.

A guest thread shares its process's address space and descriptors, so its
shadow at home must be a thread of the same shadow, not another process
(shadow_thread). What that exposed:

  Page sets were global. sh_touched/sh_orig_* were one array drained
  without the lock while each thread ran MADV_DONTNEED, so a thread could
  pair a page with another address's snapshot and write zeros into live
  guest memory. Diagnosed from a single load: netsurf read `struct pthread
  *self` as 0xc0 — the correct low byte with the upper seven zeroed. The
  sets are per serving thread now, and the fault thread attributes each
  fault with UFFD_FEATURE_THREAD_ID; a kernel without that feature is
  fatal rather than a silent fallback, because an earlier attempt at
  per-thread sets failed for want of exactly it.

  The shadow channel crossed. shadow_pread used the shared pipes without
  the lock and read its payload from sh_rsp[0] even on a private channel,
  so two threads took each other's replies.

  pick_address() is a bump allocator with a non-atomic read-modify-write,
  and it is called once per context.

The map of a real program did not fit either: a browser is ~500 mappings
and ~58 KiB of /proc/maps text, and the 64 KiB buffer truncated it in
silence.

That took the browser from 4522 syscalls to 9210, where it stopped dead in
the same place every run — a window on screen, and the page never fetched.
The cause was not in the threading at all: see "A fault on somebody else's
address space" in vmctx/README.md. execve builds the new program's argv
and envp in a bprm->mm that is not the task's mm yet, on a stack starting
one page below STACK_TOP_MAX; the fault hook reported it, the monitor
found that address already present in the *task* and answered "supplied",
and the retry faulted again forever. A GTK 4 browser hits it the first
time it decodes an image, because the loader is spawned through bwrap. The
kernel declines those faults now; vmremote declines a fault on a page this
context already has, which is the same statement from the other side and
works without a kernel rebuild. Measured: the stuck loop is gone, the
execs complete, 10133 syscalls against 9739.

The second half replaces the machinery that caused the first. sh_flush()
reconstructs which bytes a syscall wrote by diffing each page against a
snapshot taken when it arrived, because both machines write the same page
and nothing reports which bytes moved. Under VMCTX_COHERENT they do not:
a page has one holder. The shadow's fault takes it out of the guest
(VMCTX_CTL_TAKE), the guest's fault asks for it back, and sh_flush() has
nothing left to do.

The recall needs somewhere to arrive: the guest faults on its own schedule
and the shadow is usually blocked in a syscall, so the shadow gets a
thread and a connection of its own — the mirror of the page-service thread
the other end already runs for the same reason. Three things had to be
right and were wrong first, all in README.md: a page is held by an address
space and not by a context (Tgid, or every sibling thread refills it from
the oracle behind the shadow's back); a chunk fetch must skip pages out on
loan; and one lock over a transition, or the two sides race into a fault
the guest takes forever. Loans are settled before a guest forks, since
fork copies both address spaces at once.

Holding a page outright is not enough, though, and the browser proved it
by dying after ~600 syscalls. Both machines may hold a page as long as
neither may write it, and for a real program that is most of them — a
library's text, a constant table, a stack that syscall arguments point
into while the guest runs on it. With only "held" and "not held" every one
of those moved on nearly every fault.

So a fault says what it needs. A read takes a shared copy and leaves the
other side a read-only one (VMR_PG_GETS, VMR_PG_DOWNGRADE); a write revokes
the other side's copy first (VMR_PG_UPGRADE, or the guest's protection
fault, which vmremote used to count and discard). VMCTX_CTL_PROTECT is the
kernel half. That took the browser from ~600 syscalls to 10133 — the same
as the model being replaced, stopping in the same place, which is the
browser's own problem and not memory's.

Five more defects on the way, all in README.md: a page the guest has never
touched still makes the shadow its holder, or the two sides diverge in
silence from the first syscall; a settled loan must keep its slot, since
clearing a key in an open-addressed table cuts every entry that hashed
there and landed further along out of reach, and the lookup then serves the
oracle's copy over the live one; a shadow must never die holding a page,
nor drop one when a region leaves the guest's map; and /proc/self resolves
at open time, so a forked shadow inherits a pagemap descriptor and answers
"do I still have this page" by reading its parent's page tables.

The last one was the mirror mapping over itself, and the two ends
contradicted each other usefully: one said a page had been lent whole, and
the shadow holding it — alive, answering, with the right VMA — said it did
not have it. sh_mirror_one() maps MAP_FIXED, and the record that keeps it
off live memory is a second copy of the truth. A forked shadow rebuilt that
record from nothing while holding a complete copy of its parent's address
space, so it re-mapped and discarded it; what such a shadow actually lacks
is the userfaultfd registration, which fork does not carry, so registration
is now separate from mapping. And the record is not trusted anyway: the
page tables are asked before mapping, because they cannot drift.

The settlement before a fork kept reporting pages it could not get back;
asking which of its three steps had failed answered it. The shadow was
gone, so nothing could answer — and the guest had no mapping there either.
Those are the loans of a context that has finished: the address space they
describe exists on neither machine, so there is nothing to lose. Counted
now rather than reported, and the reports stopped.

Chasing the rest turned up something larger. A page request that names no
context is served as the first one, which was right while there was only
ever one shadow; counting who sends them found four different shadows all
being answered as the first guest. sh_ctx is thread-local and only the
serving threads set it, so the fault thread — which serves no context of
its own — attributed every page it fetched to the first one, taking it out
of the parent's address space to hand to a child and recording the loan
against a third party. It knows the faulting thread already
(UFFD_FEATURE_THREAD_ID, there for the page sets), and that thread's
context is the answer. The same for whoever settles pages back, which is
not always a thread with a context, so a shadow now remembers which
address space it mirrors as well. After both, no request names no context.

The last one needed a history rather than a snapshot, so the shadow keeps
one per page and replays it when a recall comes up empty. It had handed
the page back and was being asked again: a page was in flight when the
recall arrived. Between the lender deciding to lend and the copy landing
there is a window belonging to neither, and a recall arriving in it is
answered "I do not have it" — truthfully, and disastrously, because the
lender then drops the loan and serves the next fault from the program's
original bytes while the shadow finishes installing what it was sent. The
shadow now records what is on its way to it and a recall for one waits,
which cannot deadlock: the lender holds its own lock across a lend and
across a recall alike, so by the time a recall can be issued the page has
been sent, and the wait is for a copy this process alone has left to make.

That history is itself inherited across fork, so a child was explaining
its own missing page with things its parent did to a page it never had —
which reads as an answer, and is worse than silence. Reset now, as is the
"say this at most six times" counter that had the same problem: a forked
shadow inherits everything not deliberately given back, diagnostics
included, and this is the second time that has misled specifically about
forked shadows.

About one browser run in three still loses a page, and the obvious
suspicion — that the loan bookkeeping drifts — is ruled out rather than
doubted. A loan forgotten that was never recorded, which is what a clear
against the wrong address space looks like: none. A page lent to a second
shadow while a first holds it: none. Loans left by a context that has
finished: none. The report carries those counts, so a run that loses a
page says in the same breath that its records were consistent when it did.
What is left is not a lost record but a page a shadow gave up without
saying so, by a path that is neither a recall nor a settle; the three that
were — exiting, a region going away, a mapping laid over it — are closed.

loc2, th9 and th12 pass with coherence on and report no lost page. Off by
default, and with it off the old path is unchanged.

vmtake asserts the primitive underneath all of it: that a page is moved
and not copied. The bytes come back, the page is gone from the context,
and the guest re-reads zero — the last being the one a peek would pass too.

What it costs, measured with both models on the same binaries, the same
kernel and the same machine, with nothing between them but VMCTX_COHERENT
(median of five runs each):

                guest run      guest faults   forwarded   pages from home
  loc2      0.14s -> 0.14s      22 ->  32       6 ->  6     244 -> 248
  th9       0.15s -> 0.17s      22 -> 108      84 -> 84     218 -> 221
  th12      0.15s -> 0.17s      22 ->  79      53 -> 54     218 -> 221

Faults are where it costs: a page both sides touch now moves rather than
being copied and reconciled afterwards, so the monitor services two to
five times as many. What does not move is how much of the program has to
cross — pages from home and forwarded syscalls are within a percent —
which is the shape the design predicts, since the protocol changes who
holds a page and not how much has to travel. Wall clock barely notices at
this size: nothing measurable on loc2, about 13% on the threaded pair.

None of it is on the path the guest's own instructions take. The same
static binary natively and under startvm on this kernel: 232.1 Miter/s
against 232.5 in-guest, a difference inside the run-to-run spread, and
0.15 us against 1.09 us per syscall. Compute is still native; leaving the
guest is still what costs.

The browser is deliberately absent from that table. It ends at the same
GTK image decode in both models, but vmremote then waits on contexts that
outlive the guest, so every run ends on the harness timeout and vmremote
is killed before printing its counters: its wall-clock is the timeout,
not the work. What survives is how far the guest got, and it reaches the
same place either way.

=== 1671da9 2026-07-30
vmctx: the destination owns nothing, and a thread is a context like any other

The model, first, because every change here follows from it. The destination
supplies CPU and memory and decides nothing. It keeps no map: the source
performs every mmap, the address the guest holds is the source's, and this
machine finds out about memory by faulting on it. Every syscall is forwarded --
`is_local_syscall` is empty -- so a guest reading /proc/self/maps is answered by
the source and sees the source's layout. Creation is asked for and never
spontaneous: a guest clone forks at the source, which then asks the destination
for an execution context. The test each of these has to pass is that the
destination may hand back every context at any instant and the source carries on
alone.

A context's memory is a shared object -- a memfd in which a guest virtual
address is its own offset. A fault at A maps that object at A with offset A, so
two contexts started with the same object see the same page at the same address.
That is the whole of sharing an address space, and it is why threads stop being
a special case: a thread is a context handed its parent's object and a process is
one given a new object, which is the snapshot a fork wants. The destination needs
no threads, no CLONE_VM and no notion of what a thread is.

Memory is kept coherent as a protocol rather than reconstructed afterwards. A
page is shared (both sides read, neither writes) or exclusive (one side writes),
and it moves by being taken out of one side rather than copied. The old
snapshot-and-diff at syscall boundaries is gone; it existed only because nothing
reported which bytes the source had written, and the reconstruction was what
corrupted a browser's memory.

Then the defects, in the order the evidence came out.

Six of them were one root cause: the monitor decided which address space a page
belonged to by reading Tgid out of /proc. That was true while the destination's
kernel executed a guest clone. It stopped being true when a thread context began
to exist because the source asked for one -- the monitor makes it with
clone(..., SIGCHLD), so a thread context is a process of its own. Measured on a
hung th9: two contexts, Tgid 77256 and Tgid 77264, both mapping backing inode
8482. One address space reported as two, and the comment above as_id() had
already described what follows. It answers from the monitor's own record of who
shares memory with whom, which also stops the answer depending on the
destination being Linux.

What that one wrong answer cost: a thread's fault answered from the source over
its sibling's live memory, so th9's main context lost the stack it stood on and
died in __stack_chk_fail; TAKE and PROTECT acting on one context and leaving the
siblings writable; the source excluding MAP_STACK from its mirror, so every
buffer a thread put on its own stack was unreachable and forty writes of
"thread N ok" left twelve NULs each; sh_mirror_note() filling one of the two
records of the mirror, so the recall service refused every range it registered
and the source kept a stale page for ever; and nothing performing the child-exit
half of a clone, so a joining thread waited on a tid nothing would clear --
267,704 EAGAINs in forty seconds with both machines behaving as told.

The Intel target had been dead. Its kernel never got the backing_fd field,
because that tree is not in this repository and the change lived only on the
other machine; and the VMX fault path had no demand-backing at all, so the
monitor's POKE of a faulting page had nowhere to land, ever. It is one
vmctx_back_fault() both backends call now.

brk is not monotonic. A program that frees the top of its heap gives it back, the
shrink unmaps those pages and their fault registration with them, and tracking
only the high-water mark meant the regrowth registered nothing. links formats its
output into such a page: 184 of 408 bytes arrived as NULs with write(2) reporting
408, deterministically, and nothing said so -- the range was still in the mirror's
records. Found by recording, per page, the call during which the source last
fetched it, and printing that beside the bytes; a write trace shows content and
says nothing about age.

An anonymous mapping is not the destination's to fill. Recording one as "local"
declined the fault to this machine's kernel, which is the documented wrong turn:
an anonymous range is exactly where a program keeps what it computes. It is also
no longer survivable, since the module removes the backing it made when the
monitor declines, so w3m died on an unrecoverable #PF at the first byte of a
range it had just mapped.

And the page service read a page before write-protecting the guest's copy, so a
guest write landing between the two raised no fault and left the source holding a
copy one iteration old. It protects first and reads after.

Where this leaves it. The full suite passes 48/48 on the AMD box, curl of a
19.5 KB page is byte-identical, and on the Intel machine the objective's own
acceptance command --

    TARGET=10.0.0.30 ./vmctx/remote-run.sh /usr/bin/links -dump http://localhost:8080/

-- is byte-identical to native 8/8, as are w3m and curl. A residual of about
1 run in 80 remains on the threaded tests: a write emits the previous line, or
loses one, or leaves NULs in it. Sharing is not the cause -- making pages move
whole as soon as an address space has a second context changes the rate not at
all -- and the page-age record is in the tree for whoever looks next. The README
carries the measurements, the diagnoses that were wrong first, and the repairs
that were tried and reverted.

vmctx: a program handles its own faults, and the owner decides what one means

An exception is reported to whoever owns the program, as a vector and
nothing more, and the owner answers with a register set or with nothing.
Nothing on the destination decides what an exception means: that 6 becomes
one signal and 3 another is the owning system's rule, so the vector travels
unread and the frame is built where the program's memory is. An owner that
was not Linux would answer the same report differently.

Every exception the program can raise is intercepted, and one arm reports
them all. Not a list: the guest runs with no IDT, so an exception left
uncaught is not handled by the guest either -- it faults reading a gate at
sixteen times the vector, and arrives as an unrecoverable page fault at an
address that names the real exception only to someone who divides by
sixteen. #GP did that at 0xd0 and int3 at 0x30, each found the same slow
way. #UD and #PF keep their own arms ahead of it because this machinery
gives those two a meaning of its own -- a SYSCALL leaves as #UD, and a page
absent here is a page that lives on the other machine.

What had to be true, each wrong on its own:

  - The register frame carries a fault's answer, as it always has a
    syscall's. pt_regs *is* the guest's register file here -- published at
    every exit, taken back at entry -- but the fault paths did neither, so
    an owner saw the previous stop's registers and a SETREGS answering a
    fault landed where nothing read it. Publishing it back without also
    refreshing it first rolled every fault's registers back one stop, 1350
    times a run, and took the suite from 9 passing to 0. That is also the
    whole of why delivering from the #GP and #UD arms once put the context
    in the monitor's own text at 0x20003f20 and killed it -- the exits were
    never the problem, the stale frame was.

    cleared field by field, that flag survived from one reply to the next,
    so one handover made every later syscall say "carry on at the handler".
    pf1 entered its handler once and issued the same mprotect 464035 times.

  - The question "may the program make this access" is asked wherever a
    fault arrives, not only where a page is absent. Whether a page is
    present is a fact about this machine's page tables; whether the access
    is allowed is a fact about the program.

  - si_code comes from the owner's own mappings, not the reported error's
    present bit -- which describes page tables that start empty and fill on
    demand, so every mapping reads as "nothing there".

  - A trap is reported standing after the instruction, a fault standing on

    the owner is told where the program is. Reported on its own int3, tr1's
    handler decided correctly, returned, and trapped again for ever.

and by nothing else. A file or a System V segment is shared by *naming* it --
two mappings ask for the same slot in the context's own object and get the

already worked.

whose fault it is instead of inferring it.

protections live in the VMA, and the coherence protocol, which write-protects
the PTE and leaves the VMA alone. Told only an address and an error code, the
monitor decides between them from its own loan table and guesses when that is
silent -- and a guess either declines a program's own fault to a local kernel
that cannot grant it, or takes a protocol fault to the owner as a
segmentation fault.

The event's argument words are unused on a fault, so the state goes there:
whether a VMA covers the address, what it permits, and whether a page is
present and writable.

Nothing on this path may block on a lock. One of the two callers is the
kernel's own page-fault path, which arrives holding mmap_read_lock and may
hold a page-table lock; taking either again is not a slow path but a deadlock,
and a writer queued in between stops the machine. Found by doing it: the
first version took mmap_read_lock unconditionally and hung the box. So that
caller marks itself, is not inspected, and the other only tries for the lock
-- UNKNOWN is an answer, and a monitor that read it as "no mapping" would
turn every such fault into a segmentation fault.

What it says already: every fault in tests/pg2 reports vmaprot=0x7 and
present=0. The VMA is read-write-execute everywhere, because that is what the
fault path maps and the owner's protections are replayed onto the pages that
exist rather than recorded for the range. So the program's intent is largely
not on this machine at all, and the two masters cannot be told apart because
only one of them has written anything down.

=== 97221a4 2026-08-02
vmctx: the program's own machine makes its syscalls, and the destination owns nothing

Read the whole system first -- the kernel core and both backends, both userspace
halves, the wire protocol, every test and every script -- and wrote down what
each path actually does against what it says about itself. AUDIT.md is that, and
everything below is what it found or what fixing it required.

## The architecture

A monitor may not make a guest's syscall itself. It is a different process, the
same address is different memory in each of them, and every pointer argument
would be answered from the wrong memory -- which is most syscalls worth
forwarding. vmhome had been doing exactly that.

So the kernel grew VMCTX_CTL_SYSCALL: the monitor supplies a number and
arguments, and the *context* performs the call, in its own address space, with
its own descriptors, credentials and identity. Beside it VMCTX_CTL_ADOPT and the
service context -- a task that holds an address space and never executes. It
needs no virtualisation backend, which is the point: the machine that owns a
program does not have to be able to run it. And a register change mask
(including FSBASE and GSBASE), so a monitor learns what a call moved without
reading the register set twice and diffing it across a machine boundary.

tests/vmsys.c is the test for the property the whole thing exists for: both
processes map one address with different bytes, the monitor asks the context to
write from it, and whichever string comes out of the pipe names the address
space the call was made in. It caught the change mask reporting six registers
where one had changed, on its first run.

## The destination's concept of files, removed

The largest thing the audit found. struct region stored a descriptor and a path
for every range, VMR_OP_PREAD asked home to read a file by fd and offset, the
mmap arm inspected the guest's fd argument to decide whether a mapping was
file-backed, and fdpath_set/get tracked what path each descriptor was opened as.
None of it means anything on a destination that is not Linux.

It is gone. Loading a file is the program's business: it calls the kernel that
owns it, and the result is a memory map that happens to contain the file. Every
page request is now "the bytes at this address in this context" and names no
file, with the source alone deciding what backs that address.

## vmhome

7745 lines to about 2100. The shadow process, the userfaultfd mirror, the layout
sync, sh_may_access and the write-back path are all deleted -- roughly six
thousand lines that existed to make two address spaces pretend to be one.

## What was broken, and how it was found

Every advance here came from an instrument. Every confident diagnosis reasoned
from a symptom was overturned by a measurement, including several of my own.

  - A fault the program had not registered a handler for did not kill it. Three
    children, all exiting 242, all at rip 0x280623c8 inside vmhome's own text.
  - The protections a program is *loaded* with reached neither machine. Both
    sides parsed the perms column out of /proc/maps and never read it again.
  - Shared memory was an illusion inside the destination's backing object. sm3
    is the test that says otherwise: two processes, one file, two *different*
    addresses, which defeats the by-address page move that had made sm1 and sm2
    pass while this was broken.
  - do_fault_around() handed back pages the monitor had deliberately taken away,
    and every hook keyed on current->vmctx was blind to it because the faults
    doing it were the monitor's own. What identifies a context's memory is whose
    mm it belongs to, not who is touching it. Isolated with one command --
    echo 4096 > /sys/kernel/debug/fault_around_bytes -- before any rebuild.
  - A forwarded syscall did not end where a syscall ends. Signal delivery and
    -ERESTARTSYS ran one iteration later and were overwritten by the next call's
    SETREGS. The service context stood at the program's own SIGUSR1 handler with
    a complete frame in its stack while the machine running the program carried
    on past its SYSCALL and died in __printf_buffer. Ten runs out of ten.
  - System V shared memory had never once worked, silently. shmctl was issued as
    IPC_STAT|IPC_64; shmctl(2)'s own SYSCALL_DEFINE3 passes IPC_64 as a separate
    version argument and ksys_shmctl() switches on the raw command, so 0x102
    matched no case and returned -EINVAL behind an early return that logged
    nothing.
  - A MAP_SHARED file mapping is the one range observable *without* the mapping,
    so no fault ever brought the guest's stores home.

## The kernel patches were nearly right, which is worse than absent

kernel-patches/ is the only tracked record of the kernel side. Eleven patches
sat here looking complete while nine commits -- the entire architecture above --
were unexported, and all of it was *uncommitted* in src/linux-7.0.14, the kernel
the source box had been running and measured against for days, which has no
remote. Both trees are now committed and fully exported, and the README says why
they differ rather than inviting anyone to sync them.

## Tests

Each controlled natively before being believed: pf3, pf4, sig1, fi2, sm2, sm3,
rd1, fm1, vmsys. suite.sh's xfail mechanism had no user at all, so its summary
always read "0 known gaps"; it now marks the ones that are.

pg2 counted a short read and a wrong byte as one number, so "297 of 300 bad
payloads" read like wholesale page corruption when it is also what a read(2)
returning the wrong count looks like -- different defects on different sides of
the machine. It now separates them and reports the first bad round in full,
which is what showed the bytes are zeros rather than stale data.

## A page pinned by a device, which nothing here could see

Removing a page's page tables is not the same as removing every way to reach it.
A syscall this side performs pins its buffers with get_user_pages() and holds
the reference for the whole call; a driver may hold a kernel mapping; a device
may already have the physical address in a descriptor. None of that is undone by
a zap or by unmap_mapping_range(). So a page handed to the other machine while
any of it is outstanding is one this machine can still write, after the other
machine has been told it owns it.

vmctx_folio_may_move() now refuses a hand-over while the page is DMA-pinned or
still mapped, and waits out writeback. -EBUSY means "not yet": both callers wait
and ask again, which is the escalation lock stated where the facts are rather
than inferred in userspace from syscall boundaries.

tests/dma1.c is the case, and it had no coverage at all: a read with O_DIRECT
pins the buffer and hands it to a storage controller, while a second thread
gives the far side a reason to claim the same page. Native, 0 bad rounds out of
200. Under vmctx, 22 to 200 bad -- memory a device wrote into a page that had
been given away. Listed as a known gap, because the two checks that are in do
not catch it: the one that would is a reference-count comparison against
folio_expected_ref_count(), and it is not usable without isolating the folio
from the LRU first, which is not built. Its removal is its own commit.

## Not fixed, and recorded rather than worked around

  - pg2's "bad payloads", now traced to a protocol gap rather than a defect in
    any function. A fault on a page the source holds now asks for it with
    VMR_OP_CTXPAGE -- the pull the protocol is built on -- instead of trying a
    recall over a channel that does not exist and then falling through to a
    path that declines, which the local kernel answers with a freshly allocated
    zero page that the guest then never faults on again. Traced at
    0x7ffff7ff6000: thirteen clean rounds, one LOST line, then no activity on
    the page at all while the program read 0x00 for 287 rounds. With the pull
    the page keeps moving -- 19 pulls, all returning a page -- and the failure
    changes shape: the same payload is handed over twice in a row, because
    nothing keeps a page at the source for the length of a forwarded syscall.
    The guest's second thread faults on the buffer and pulls it back while the
    source's read(2) is still in flight, so the source writes into a page it no
    longer owns.

    What that needs is an escalation lock: while this side is performing a
    call, a page it has pulled for that call may not be given back until the
    call returns, and the far side waits rather than being served a page the
    call is still writing. No new channel is needed, because this side is the
    one that starts the call.

    Written, measured, and reverted, both ways round. Holding every page for
    the length of the call passes pg2 9 to 12 times out of 12 against a
    baseline of 4 -- and takes the suite from one failure a round to twenty,
    because a call that blocks (poll, wait4, a read with nothing ready) holds
    every page request behind it and the 2s timeouts cascade. Holding only the
    pages the call has actually pulled is the right shape and demonstrably
    live -- 614 pages held, 209 requests made to wait, 517 let through in one
    run -- and still leaves six failures a round.

    So the mechanism is right and this implementation of it is not, and it is
    out of the tree rather than left in as a regression. What it is missing is
    most likely that a page request must be made to wait *without* stalling
    the contexts that are not touching that page at all; getting that right
    probably means the kernel performing the call saying which pages it will
    touch, rather than this side inferring it from faults after the fact.
    Four hypotheses have been tested and refuted -- guest TLB staleness, a copy
    taken while siblings still write, memfd SEEK_DATA misreporting a punched
    hole, and the fault hook's exclusion of VM_SHARED. The last was instrumented
    in the kernel and fired zero times against a control of 153 other vmctx
    messages in the same runs.
  - pg2's other failure, torn pages, is fixed: the hand-over is now one kernel
    operation over the whole address space (VMCTX_CTL_TAKEOBJ) rather than a
    per-context sequence with a gap at every join. Tears went 8 across twelve
    runs, to 1, to 0 across eight.
  - Seven of the twelve page operations have no client left: vmhome sends no
    PUT, PUTN, PUTV, RECALL, HELLO_RECALL, DOWNGRADE or UPGRADE. Measured on one
    run: 321 pages handed over, 0 recalled, 0 shared, and 320 LOST lines. The
    dead machinery is load-bearing anyway -- removing the recall block killed
    the program outright, because it is also what clears the loan record.
  - rd1's initial-guest, initial-forward and exit-writeback.
  - A signal with a handler is delivered at the context's next forwarded
    syscall, not at an arbitrary instruction boundary.
  - src/linux-6.18.35 does not carry the signal work. Correct while .30 is the
    destination; a defect the moment it is asked to be a source.

vmctx: a guest may grow its stack, and a page nobody mapped is not installed

/usr/bin/wc would not run. Neither would anything else built in the last
decade, and the reason had nothing to do with the two machines: a VM context
could not grow its stack at all.

Compilers emit a stack-clash probe loop for any frame bigger than a page --

	movq $0, (%rsp) ; cmp %r11, %rsp ; jne .- ; sub $imm32, %rsp

-- which walks rsp down a page at a time. The first probe below whatever the
loader touched is an ordinary VM_GROWSDOWN fault, and the architecture's own
handler answers it by expanding the stack. A context's faults never reach that
handler: they are serviced with fixup_user_fault(), which looks the address up
and returns -EFAULT when it falls below the VMA, because since stack expansion
moved into lock_mm_and_find_vma() no GUP-side path grows a stack. The guest
died on the first frame deeper than the one it started on:

	vmctx: usercode: unrecoverable guest #PF at 0x... err 0x6 (-14)
	vmctx:   insn @rip: 48 83 0c 24 00 4c 39 dc 75 ef

tests/stk1 is that, in twenty lines: walk 256 KiB down, a page at a time, and
read it back in the other order. It reproduces with no monitor and no second
machine -- `startvm tests/stk1` -- which is what says this was never about the
distributed part.

expand_stack() is not exported, so the module touches the page the way the
program would, from the task's own context: a kernel-mode access to a user
address goes through do_user_addr_fault() -> lock_mm_and_find_vma(), which
grows the VMA with the guard gap and RLIMIT_STACK applied, and
get_mmap_lock_carefully() permits it because get_user/put_user carry an
exception-table entry. The probe matches the direction of the fault and must:
a read probe installs the shared zero page and vmctx_wp_fault() then refuses
the write, so the guest would take a SIGBUS instead of a page. Measured,

"the local kernel now answers this". It cannot -- a context maps nothing in

VMA. Serving it here was right; writing it into the backing object was not.
The module backs the address from the object before asking, then takes the
monitor's word, because every other answer arrives as a POKE through the
mapping and populates the page as a side effect. An object write leaves the
PTE empty, the guest retakes the same fault forever, and at forty vmremote's
own watchdog answers VMCTX_ACT_KILL:

	[stuck] addr=0x7ffffffdd000 err=0x6 present=0 installed=1
	[stuck] VMA: 7ffffffdd000-7ffffffde000 rwxs /memfd:vmctx-guest

a VMA that exists, a record saying the page is here, and no page. That killed
wc as "exit 131", which is -ECANCELED through do_exit((status & 0xff) << 8) --
indistinguishable from exit(131) to anything reading a wait status, and named
nowhere. The teardown line added here says which branch a context left by, and

=== 8d05230 2026-08-09
vmctx: a page can leave this side between the read and the take; that is ABSENT

pg3 aborted vmremote about 5 times in 40 runs, and it is a valid test: 200 of
200 natively. The abort:

	FATAL: 0x7ffff7ff6000 is present in address space N but no context
	would hand it over (last errno: No data available)

The sequence, from the FATAL's own context dump:

  1. page_read_as() finds the page in NO context and answers from the backing
     object -- which is the normal state between a take and the next fault,
     since a take clears the page tables and leaves the bytes in the object;
  2. page_take_away() then finds no context to take from;
  3. its object fallback re-reads the object and finds nothing;
  4. abort().

Step 3 is the whole thing: the object had the page in step 1. Between them a
concurrent hand-over punched it out -- fallocate(PUNCH_HOLE) after a take, or
shmem_truncate_range() inside TAKEOBJ. The read and the take are not atomic with
respect to the object, and backing_has() (an lseek(SEEK_DATA)) is asked again in
between.

The guard the abort implements -- "refusing to answer ABSENT over real memory"
-- is right, and simply does not apply once the page has gone: there is no real
memory on this side to answer over. So it is checked rather than assumed. If no
context has the page AND the object does not have it, this side genuinely does
not hold it, and ABSENT is *true*: the asker's own copy is the current one,
